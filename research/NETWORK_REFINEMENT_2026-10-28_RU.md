## Продукт и путь пользователя

Сохранены существующие художественные сцены, подпись, бумага, чёрная ткань, золотая гравировка, фуксия и заголовок **The other side.** Сразу после заголовка объясняется коммерческое назначение сети: международные компании → платёжные провайдеры, локальные операторы и коммерческие партнёры в Asia / LATAM / Africa.

Главная больше не собирает индустрию, страны и capabilities в отдельной большой форме. ConnectionStudio выбирает намерение и одну из шести ролей, затем передаёт контекст в единственный Connection Engine. Если намерение ещё не выбрано явно, роль предлагает естественную сторону; явный выбор пользователя сохраняет приоритет.

Шесть сценариев:

| Участник | Контекст брифа |
|---|---|
| International Merchant | Категория бизнеса, приём, выплаты, локальные методы и выход на рынок |
| PSP / Payment Aggregator | Недостающая локальная инфраструктура, операционная ответственность и дистрибуция |
| Local Payment Partner | Приём, выплаты, методы, локальные расчёты и интерес к международным PSP |
| Exchange / OTC Business | Направления, активы, ликвидность и роль контрагента |
| Affiliate / B2B Introducer | Возможность организовать знакомство, разрешение на раскрытие и коммерческий интерес |
| Strategic Partner | Экспертиза, технологии, дистрибуция и совместный коммерческий результат |

В форме два этапа: задача → контекст и контакт. Полный корректный deep link сразу открывает контактный этап со сводкой и действием «Изменить задачу». Методы, расчёты и дополнительные сведения раскрываются по необходимости. Для платёжного предложения доступны необязательные сведения об операционной/лицензионной роли; это заявление участника, которое не меняет статус verification.

Переключение просматриваемого региона сохраняет уже выбранные страны других регионов. Удаление страны очищает только ставшие нерелевантными методы и валюты. Черновик сохраняется в сессии; после подтверждённой отправки контактные сведения очищаются. На ошибке остаются бриф, безопасный retry и подготовка письма/копирование без ложного receipt.

Industries доступны в основном desktop-меню и мобильном меню. Exchange / OTC остаётся одной из индустрий; большая художественная сцена объясняет несколько равноправных B2B-направлений.

## Надёжность и приватные операции

Существующие транзакционное сохранение, outbox, additive migration, история и коммерческий учёт сохранены. Изменения:

- Gateway требует точный HTTPS origin и общий секрет не короче 32 символов; не допускает петлю на текущий host.
- Дублирующий `_route`, неразрешённые пути/методы и oversized body отклоняются. Buffer передаётся без повторной JSON-сериализации. Ошибки чтения тела обрабатываются контролируемо.
- Редирект upstream не выдаётся за сохранённую заявку. Все ответы gateway имеют `no-store`; ошибки доступности получают `Retry-After`.
- Клиент признаёт успех только при корректных `status: received` и VN reference.
- Существующий request ID может вернуть сохранённый reference даже после лимита новых обращений. Изменённый нормализованный payload под тем же ID по-прежнему получает 409.
- Production Node отказывается стартовать с placeholder admin key, коротким gateway key или несовпадающими public/allowed origins.
- Приватные административные изменения, включая сохранённые старые API, проверяют Origin; `/admin` и API не индексируются и не кешируются.
- Получение health подтверждает доступность SQLite и отдельно сообщает, настроены ли уведомления. Оно не доказывает доставку в реальный канал.
- Операционный и коммерческий контекст сохраняется в общей модели opportunity. Source, medium, campaign, ref, landing и referrer доходят до приватной записи. Referral attribution остаётся неподтверждённой до коммерческого соглашения.
- Deal Desk фильтрует реальные источники и обращения с наступившей датой follow-up; новый таб показывает реальные задания уведомлений, неудачные попытки и срок повтора.
- Кандидаты по-прежнему берутся только из сохранённых проверенных записей. Явно несовместимые методы/валюты исключаются. Кандидат не становится подтверждённым match автоматически.
- Перед переводом предложенного знакомства в фактическое повторно проверяются актуальность, verification, совместимость и разрешение обеих сторон. Отзыв согласия блокирует продолжение.
- Изменение знакомства отражается в истории обеих сторон. История квалификации показывает понятные изменения, а не большой сырой JSON.
- Назначить follow-up для непроверенного обращения можно без фиктивных verification evidence. Проверенный статус и согласие на передачу по-прежнему требуют подтверждений.

В уведомлении остаются только `{event, id, reference, deskPath}`. Доставка — at least once; получатель обязан устранять дубли по стабильному `Idempotency-Key`. Не заявляется exactly-once доставка Telegram. Retry, lease и recovery проверены на отдельной базе и локальном реальном HTTP-получателе.

## Telegram

На Contact добавлена существующая публичная группа `https://t.me/vladdos_network` с явным указанием публичности. Конфиденциальные заявки направляются в бриф или email. Официальный канал и Connect Bot не изображаются работающими.

Для будущего Connect Bot достаточно отдельного адаптера: принимать бриф только в приватном чате, аутентифицировать сервисный доступ, передавать сведения через тот же валидатор и intake API, использовать стабильный request ID и сохранять происхождение Telegram. Операционные уведомления получает отдельный приватный получатель outbox. Согласие на рассмотрение не заменяет разрешение на знакомство. Публичная группа не должна быть получателем контактов или коммерческих брифов.

## SEO, язык и доступность

`networkMeta()` стал единственным источником route metadata. Старый `src/data.ts` экспортирует его для совместимости. Страны и основные коммерческие маршруты имеют разные описания.

Язык определяет URL; сохранённая настройка не подменяет EN-страницу русским содержимым под EN canonical. SSR и клиентская навигация обновляют title, description, canonical, EN/RU/x-default alternates, OG, Twitter и structured data. Приватные/неизвестные страницы получают noindex. Статический sitemap теперь включает x-default, как серверный sitemap.

Сохранены старые ссылки и query context. Неизвестные legacy роли теперь одинаково разрешаются Node, React и Vercel. Внутренние prerender-файлы не выдаются Node напрямую и получают noindex при прямом запросе к Vercel.

Сохранены self-hosted fonts, lazy loading сцен, high-priority hero и reduced-motion CSS. Форма имеет обычные fieldset/legend, нативные поля, видимые состояния, фокус на ошибке/receipt и управление с клавиатуры. При смене маршрута фокус переводится в основной контент.

При визуальной проверке устранены обрезка EN hero на узком экране и меню, пересекавшее тёмную ткань. На desktop добавлена спокойная бумажная подложка навигации и контекстного абзаца. На мобильном сохранена исходная композиция изображения над текстом.

## Внешние действия до выпуска

1. Определить реальный persistent Node/Docker сервис, его HTTPS origin, host access и постоянный SQLite volume. Если уже существует база, использовать её с сохранением identity/volume; не создавать пустую базу вместо неё.
2. Создать проверяемую приватную consistent backup и открыть её копию. Сравнить исходные counts/references и очереди. Не использовать реальные данные в открытом preview.
3. Настроить на сервисе `ADMIN_TOKEN`, `DB_PATH`, `PUBLIC_SITE_URL=https://www.vladdos.com`, `ALLOWED_ORIGIN=https://www.vladdos.com`, общий `INTAKE_GATEWAY_TOKEN`. Gateway secret должен совпадать на Vercel и сервисе.
4. Настроить реальный приватный HTTPS notification receiver и `NOTIFICATION_WEBHOOK_URL` / `NOTIFICATION_WEBHOOK_SECRET`. Подтвердить deduplication, retry и отсутствие контактов в событиях. Для Telegram нужны настоящий бот и приватный destination; публичная группа не подходит.
5. Установить `INTAKE_SERVICE_ORIGIN` и gateway secret в нужном окружении существующего Vercel проекта. Preview должен использовать отдельный тестовый backend/database, а не production volume.
6. Проверить операционные/юридические реквизиты реального оператора перед расширением публичной работы. Текущий доступ Deal Desk рассчитан на одного уполномоченного оператора; многопользовательская RBAC здесь не заявлена.

## Безопасный deploy и rollback

1. Зафиксировать кандидатный commit и image digest. Выполнить build/check/tests и review diff. Секреты не включать в образ, Git или публичный frontend.
2. На приватной копии базы запустить кандидата и проверить старые references, legacy API и сохранённую коммерческую историю. Миграции не удаляют таблицы и не меняют прежние references.
3. Поднять один persistent экземпляр с прежним volume `pan-data`, HTTPS и backup. Сохранить действующие настройки growth; для первого smoke не включать новые AI-публикации без отдельной настройки.
4. Подготовить preview/staged deployment. При release через Vercel использовать staged production deployment с production env, затем проверить именно его до назначения доменов. Простая публикация статических файлов P0 не исправляет.
5. Выполнить **реальный** designated test brief → reference → authenticated desk row → acknowledgement приватного получателя. Проверить EN/RU source, canonical/alternates после SPA-перехода, отсутствие публичного noindex, legacy redirects, API auth и 404. Отметить синтетическую заявку как QA, не удалять реальные записи.
6. Только после прохождения gate назначить production domain. Контролировать реальные ошибки, сохранение заявок и pending/retrying queue. Здесь домен не переключался и release не выполнялся.
7. Для frontend rollback использовать зафиксированный deployment `dpl_ELGWaDhxy1TDmuDXxfssE122wFXa` / URL снимка. Для backend сначала вернуть предыдущий image, сохранив текущий volume; additive данные и новые поля не требуют отката базы.
8. Восстановление базы из backup — отдельная аварийная операция с остановленным writer и сверкой заявок после времени backup. Не заменять живую базу старой копией: это потеряет новые обращения. Сохранить текущую базу приватным recovery artifact.

Прежний production deployment тоже имеет неработающий intake. Rollback возвращает прежний frontend, но сам по себе не устраняет отсутствие backend.
